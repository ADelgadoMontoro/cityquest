# EVO-0033 - Register Objective Completion in D1

## Epic

`Backend MVP`

## Objective

Persist the first real objective-completion event in D1 after the mobile flow has passed the
temporary validation sequence.

This EVO should turn the current in-memory/mock completion moment into a backend-recorded event,
without pretending that authentication, final anti-cheat validation, full user progress, route
completion, achievements, or analytics already exist.

## Why This Task Exists

The repository now has a coherent MVP gameplay path:

- real route and objective payloads from the Worker API;
- real image capture/selection on device;
- real client-side GPS proximity checking;
- local mock visual validation;
- real unlockable content delivered from D1;
- mobile navigation from objective to unlocked reward.

The remaining problem is that the system still forgets the completion as soon as the user leaves
the screen. There is no backend record that says:

- which objective was completed;
- by which temporary actor;
- through which validation mode;
- at what time.

`EVO-0033` exists to introduce that first persistence point.

## Current Repository Reality

At the time of this EVO:

- the content schema exists for destinations, routes, POIs, visual objectives, hints, and unlocks;
- there are no user, session, or progress tables yet;
- auth is intentionally deferred;
- mobile can already produce enough local signals for a temporary completion:
  - image exists;
  - GPS was in range when a radius exists;
  - visual mock passed.

That means this task should focus on a narrow completion record rather than a full progress
platform.

## Recommended Product Boundary

This EVO should persist a completion for a **temporary actor**.

Recommended temporary actor strategy:

- mobile sends a stable local `actorId`;
- for now that actor can be a demo/guest identifier generated or stored locally by the client;
- backend treats it as an opaque string;
- later auth work can replace or link this actor to a real user identity.

Do not introduce real login in this task.

## Technical Goal

Add a backend write path that lets mobile record that an objective was completed by a temporary
actor after the current mock validation flow succeeds.

Recommended endpoint:

```txt
POST /objectives/:objectiveSlug/completions
```

Recommended request body:

```json
{
  "actorId": "guest-local-device-or-demo-id",
  "routeSlug": "jaen-echoes-of-stone",
  "validationMode": "mock_visual",
  "gpsStatus": "within_radius",
  "visualStatus": "passed"
}
```

Recommended response:

```json
{
  "success": true,
  "data": {
    "completion": {
      "id": "completion-...",
      "actorId": "guest-local-device-or-demo-id",
      "objectiveSlug": "estatua-san-fernando",
      "routeSlug": "jaen-echoes-of-stone",
      "validationMode": "mock_visual",
      "completedAt": "2026-..."
    }
  }
}
```

The exact ID strategy can follow existing repo conventions, but it must be deterministic enough for
tests and safe enough for repeated local development.

## Data Model Guidance

Add the smallest table that can support objective completion:

```txt
objective_completions
```

Suggested columns:

- `id`
- `actor_id`
- `route_id`
- `objective_id`
- `validation_mode`
- `gps_status`
- `visual_status`
- `completed_at`
- `created_at`
- `updated_at`

Recommended constraints:

- foreign key to `routes(id)`;
- foreign key to `visual_objectives(id)`;
- uniqueness on `(actor_id, objective_id)` to make repeated completion idempotent;
- indexes by `actor_id`, `route_id`, and `objective_id` if useful.

Recommended behavior on repeated completion:

- do not create duplicates;
- return the existing or upserted completion record;
- keep the endpoint safe to retry from mobile.

## Scope

This task should include:

1. add a D1 migration for objective completion persistence;
2. add tests proving the migration creates the table, constraints, and indexes;
3. add an API service that resolves published route/objective records;
4. add an API route handler for `POST /objectives/:objectiveSlug/completions`;
5. validate the request body strictly enough for the MVP;
6. persist a completion for a temporary `actorId`;
7. make repeated calls idempotent;
8. return a stable JSON response;
9. add integration tests for success and important failures;
10. update API documentation.

## Mobile Integration Scope

There are two acceptable implementation shapes.

Preferred for this EVO:

- wire mobile to call the new endpoint after `Validate Objective (Mock)` passes;
- keep the local reward navigation behavior;
- show an error if completion persistence fails before opening reward.

Acceptable fallback if this becomes too large:

- implement the backend endpoint first;
- leave mobile consumption for a follow-up EVO.

Given the current state of the app, the preferred path is small enough and more valuable.

## Non-Goals

This EVO must not:

- implement authentication;
- create real user accounts;
- implement route start/progress summary;
- calculate route completion percentage;
- award achievements;
- implement final image recognition;
- upload captured images;
- store GPS coordinates;
- store image URIs;
- build an admin progress dashboard;
- implement analytics events beyond the completion row.

## Validation Semantics

For this task, backend should not independently prove the visual or GPS result.

The backend records a completion that came from the current MVP validation mode. That means:

- `validationMode` should clearly identify the temporary nature, e.g. `mock_visual`;
- `gpsStatus` should preserve the client-reported status;
- `visualStatus` should preserve the client-reported status;
- docs must say this is not yet server-authoritative validation.

This is a product honesty requirement, not just a naming preference.

## Error Cases Worth Covering

API tests should cover:

- unknown objective slug;
- objective exists but route slug does not match;
- missing `actorId`;
- invalid `validationMode`;
- invalid GPS or visual status;
- repeated completion request for the same actor/objective;
- non-`POST` method behavior if the router requires explicit handling;
- malformed JSON body.

Mobile tests should cover, if mobile is wired in this EVO:

- completion API called only after local gates pass;
- reward is not opened when completion persistence fails;
- repeated completion response still lets the user continue;
- service maps response payload into mobile shape.

## UX Guidance

The mobile UI should remain calm and clear.

Reasonable states:

- `Saving completion...`
- `Completion saved`
- `Could not save completion`

Avoid language like:

- `verified by server`;
- `AI confirmed`;
- `officially completed`;
- `achievement awarded`.

The app can say the MVP completion was saved, but should not imply the final production validation
system exists.

## Acceptance Criteria

- D1 has a versioned table for objective completions;
- `POST /objectives/:objectiveSlug/completions` persists a completion for a temporary actor;
- repeated calls for the same actor/objective do not create duplicate rows;
- unknown or mismatched route/objective requests return controlled errors;
- request validation rejects malformed or unsupported payloads;
- completion persistence is documented as MVP/mock-mode progress;
- mobile calls the endpoint after local mock validation passes, unless explicitly split into a follow-up;
- tests cover the main success path and key edge cases;
- API build and tests pass;
- mobile typecheck, lint, and tests pass if mobile is touched.

## Definition of Done

This EVO is complete when CityQuest can record an objective completion in D1 for the current MVP
validation flow, using a temporary actor identity and honest validation metadata, without expanding
into full authentication, route progress, achievements, or production-grade verification.

## Suggested Implementation Order

1. add the `objective_completions` migration;
2. update migration tests;
3. add backend models and mapper for completion response;
4. implement the D1 completion service with idempotent behavior;
5. add the route handler and router entry;
6. add Worker integration tests;
7. document the endpoint in `apps/api/README.md`;
8. add mobile service call if keeping mobile integration in scope;
9. call the service from `CurrentObjectiveScreen` after local gates pass;
10. run API and mobile checks.
