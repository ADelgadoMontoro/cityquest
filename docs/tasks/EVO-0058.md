# EVO-0058 - Create POI Objectives Screen and Basic Progress Navigation

## Epic

`App Mobile MVP`

## Objective

Create a dedicated mobile screen for the objectives of a selected POI, showing which objectives are
completed, which one is currently playable, and which future objectives are locked.

This should make the route flow easier to understand now that the app can persist MVP objective
completion in D1.

## Why This Task Exists

The current route flow still behaves as if each route only had one meaningful action:

- open the current objective;
- complete the temporary GPS plus mock visual validation;
- open the reward.

That was enough while the MVP only needed a single vertical slice, but the content model already has
multiple objectives per POI. After `EVO-0033`, the backend can remember completed objectives for a
temporary actor, so the user needs a clearer way to:

- see objectives inside each POI;
- revisit completed rewards;
- identify the current playable objective;
- understand that later objectives are locked for now.

Without this screen, `Route Detail` will become crowded and the gameplay progression will feel
opaque.

## Current Repository Reality

At the time of this EVO:

- route detail already exposes POIs and ordered objectives from `GET /routes/:routeSlug`;
- mobile already derives the current objective from the route payload;
- mobile can open the current-objective gameplay screen;
- mobile can open an unlocked reward screen for an objective;
- `POST /objectives/:objectiveSlug/completions` persists a temporary-actor completion;
- there is not yet a read endpoint for completion/progress state.

That means this EVO should include both a small backend read contract and the mobile navigation
surface that consumes it.

## Product Behavior

From `Route Detail`, the user should be able to enter a POI-level objectives screen.

For each objective in that POI:

- completed objectives should be enabled and clickable;
- clicking a completed objective should reopen its reward content;
- the current objective should be visually highlighted and clickable;
- clicking the current objective should open the existing current-objective gameplay screen;
- future objectives should appear disabled/greyed out;
- future objectives should explain that they unlock after previous objectives are completed.

The intended mental model is:

```txt
POI
  Completed objective -> reopen reward
  Current objective   -> continue gameplay
  Locked objective    -> visible but not clickable
```

## Recommended Backend Contract

Add a route-progress read endpoint for the temporary actor.

Recommended endpoint:

```txt
GET /routes/:routeSlug/objective-progress?actorId=cityquest-local-demo-actor
```

Recommended response shape:

```json
{
  "success": true,
  "data": {
    "route": {
      "slug": "jaen-echoes-of-stone",
      "title": "Jaén: Echoes of Stone"
    },
    "actorId": "cityquest-local-demo-actor",
    "objectives": [
      {
        "objectiveSlug": "estatua-san-fernando",
        "poiSlug": "catedral-de-jaen",
        "status": "completed",
        "completedAt": "2026-07-19T17:21:41.608Z"
      },
      {
        "objectiveSlug": "mona-catedral-jaen",
        "poiSlug": "catedral-de-jaen",
        "status": "current",
        "completedAt": null
      },
      {
        "objectiveSlug": "placa-santa-catalina-coro",
        "poiSlug": "catedral-de-jaen",
        "status": "locked",
        "completedAt": null
      }
    ]
  },
  "meta": {}
}
```

The exact shape can change if the implementation finds a cleaner local convention, but the response
must let mobile derive status per objective without duplicating completion rules in the UI.

## Progress Rules

For the MVP, use a simple ordered progression:

1. objectives are ordered by POI order and objective display order;
2. completed objectives are read from `objective_completions`;
3. the first non-completed objective inside each POI is `current`;
4. all later non-completed objectives inside that same POI are `locked`;
5. if all objectives in a POI are completed, all objectives in that POI are `completed` and there is no current objective for that POI.

This is intentionally route-local and temporary-actor based.

Do not introduce a full user progress platform here.

## Mobile Screen

Add a screen conceptually named:

```txt
PoiObjectivesScreen
```

It should receive at least:

- `routeSlug`;
- `poiSlug`.

It can derive route and POI detail from the existing route-detail service and merge that with the
new objective-progress service.

Recommended UI sections:

- route/POI header;
- short POI context;
- objective list;
- back button to route detail.

Recommended objective card states:

- `Completed`
  - enabled;
  - strong completion marker;
  - CTA copy: `View Reward`;
- `Current`
  - enabled;
  - visually prominent;
  - CTA copy: `Continue Objective`;
- `Locked`
  - disabled;
  - muted/greyed;
  - helper copy: `Complete previous objectives first`.

## Route Detail Changes

Update `Route Detail` so each POI can open its objectives list.

Reasonable options:

- each POI card gets a `View Objectives` button;
- remove the old `Open Current Objective` shortcut once POI objectives navigation is verified;
- objective continuation should happen from the POI objectives screen.

## Completed Reward Reopen Behavior

When a completed objective is selected:

- navigate to the existing unlocked-story screen;
- pass `routeSlug` and `objectiveSlug`;
- read the reward from `GET /objectives/:objectiveSlug/unlocks` as today;
- do not re-run GPS, image capture, or mock validation.

This is important because completed rewards should be revisitable.

## Current Objective Behavior

When the current objective is selected:

- navigate to the existing current-objective gameplay screen;
- preserve the same validation behavior that existed before the POI objectives screen;
- keep GPS/image/mock validation gates unchanged.

## Locked Objective Behavior

Locked objectives should:

- be visible;
- be non-clickable;
- clearly communicate why they are locked;
- not expose reward content;
- not let users jump directly to validation.

## Non-Goals

This EVO must not:

- implement authentication;
- introduce real user accounts;
- implement route start sessions;
- implement achievements;
- implement analytics;
- create a full progress dashboard;
- upload or persist photos;
- implement real visual recognition;
- build demo-mode bypasses;
- replace the existing unlocked-story screen.

## Edge Cases

Cover these cases in tests where practical:

- actor has no completions yet;
- actor has completed the first objective only;
- actor has completed all objectives in a POI;
- route exists but has no objectives;
- requested POI slug does not exist in the route;
- progress endpoint receives missing `actorId`;
- progress endpoint receives unknown route slug;
- completed objective has no published reward;
- mobile receives progress for an objective missing from route detail;
- repeated completion does not duplicate state.

## Testing Strategy

Backend tests should cover:

- progress endpoint success with completed/current/locked statuses;
- empty completion set;
- all-completed route;
- missing actorId validation;
- unknown route response;
- route ordering across multiple POIs.

Mobile unit/integration tests should cover:

- progress response mapping;
- POI objective list derivation;
- completed card navigates to reward;
- current card navigates to current objective;
- locked card does not navigate;
- route-detail POI entry point is present.

Do not introduce full UI automation in this EVO unless the existing mobile test setup already makes
it cheap. Service and pure-state tests are enough if UI test infrastructure would become the real
task.

## Suggested Implementation Order

Recommended order:

1. add the backend progress query/service using `routes`, `pois`, `visual_objectives`, and
   `objective_completions`;
2. expose `GET /routes/:routeSlug/objective-progress`;
3. cover backend status derivation with Worker integration tests;
4. add a mobile service to fetch objective progress for the demo actor;
5. add a pure mobile helper that merges route detail objectives with progress statuses;
6. add `PoiObjectivesScreen` and wire completed/current/locked card behavior;
7. add a `View Objectives` entry point on each POI in `Route Detail`;
8. remove the old `Open Current Objective` shortcut once the POI objectives flow is verified;
9. update API/mobile docs and backlog status;
10. run API tests, API build, mobile typecheck, mobile lint, and mobile tests.

This order keeps the progress contract stable before the UI depends on it.

## Acceptance Criteria

- API exposes route objective progress for a temporary actor;
- mobile can open an objectives screen for a selected POI;
- completed objectives are clickable and reopen reward content;
- the current objective is clickable and opens the gameplay screen;
- locked objectives are visible but disabled;
- route detail exposes a clear entry point to POI objectives;
- the implementation does not claim production-grade auth or validation;
- API tests pass;
- mobile typecheck, lint, and tests pass.

## Definition of Done

This EVO is complete when a user can inspect a POI, understand which objectives are completed,
continue the current objective, and revisit completed rewards without losing the simplicity of the
current MVP flow.
